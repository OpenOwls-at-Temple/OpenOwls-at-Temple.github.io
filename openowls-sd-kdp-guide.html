Your Oracle

SD-KDP applies spec-driven thinking to knowledge projects — declare whose knowledge you trust, then distill it into something you can query.

Section 01

SDD Builds Software. SD-KDP Builds Knowledge.

OpenOwls has two spec-driven frameworks, and the first thing to get straight is which one your project needs.

OpenOwls SDD — Spec-Driven Development — is for building software. You write specs describing an application, then Claude Code builds it. The thing that ships is a running app.

OpenOwls SD-KDP — Spec-Driven Knowledge Distillation Process — is for building knowledge. You write specs describing a body of knowledge and whose interpretation of it you trust, then a pipeline collects that material and distills it into summaries you can query. The thing that ships is a distilled, searchable knowledge base. If your project is fundamentally a summarization or digestion project — reading a large pile of sources and turning it into answers — this is the framework for it.

  OpenOwls SDD OpenOwls SD-KDP
What you build A running application A distilled, queryable body of knowledge
What ships Source code, deployed Articles and FAQ in wiki/, plus a retrieval index
The specs describe What to build, how to build it, how to ship it Whose knowledge to trust, how to collect it, how to distill it
Who does the work Claude Code, in an interactive session A batch pipeline, running unattended overnight
Definition of done A real user completes the primary workflow end to end The Oracle's key questions are answered accurately, in the Oracle's voice

What the two share is the core habit: write the specs first, keep them in version control, and use them to brief your AI. SD-KDP simply points that habit at a different output.

Naming note: SD-KDP spec files use underscores (domain_knowledge.md), while OpenOwls SDD uses hyphens (domain-knowledge.md). They are different frameworks with different file sets — the naming difference is a useful reminder of which repository you are in.
Section 02

The Oracle — and Why Bias Is the Point

An Oracle is a perspective plus the body of knowledge it trusts. It is the single most important decision in an SD-KDP project, and everything else in the specs follows from it.

A person
Canon: their own books, letters, talks

An individual whose philosophy you want to learn — an investor, a scientist, an author. The distilled base answers as that person would, from what they actually published.

An institution
Canon: official publications

An organization with an official position and a public record — a central bank, an agency, a standards body. The canon is that institution's own publications.

A site or knowledge base
Canon: the site's own articles

A curated reference whose editorial voice you trust. The canon is that site's articles, distilled into a form your project can query directly.

Why commit to one lens

Ask a general-purpose model a contested question and it will average every viewpoint into careful, hedged consensus. That is the right default for a general assistant and the wrong one when you are trying to learn how a particular expert thinks.

SD-KDP deliberately commits to one lens and one canon. That declared bias is not a flaw to be corrected — it is the product. oracle.md asks you to state the intended bias plainly, name the sources the Oracle trusts, and name the ones it rejects, so the bias is visible, reviewable, and in version control rather than smuggled in by accident.

The framework then defends that commitment at every stage: collection skips rejected sources outright, distillation runs a voice check that rejects drift toward generic consensus, and every article has an optional "What this Oracle avoids / rejects" section that keeps the contrast explicit.

The honesty guardrail. Declaring a bias is not the same as hiding one. oracle.md requires you to present distilled answers as this Oracle's view, not as objective universal truth. A reader should always know whose lens they are looking through.
Section 03

The SD-KDP File Structure

Every SD-KDP project follows this layout. CLAUDE.md and progress.md sit at the root and are read first. The seven files inside ai_specs/ are the source of truth; src/ holds the pipeline that acts on them.

sd-kdp/
├── CLAUDE.md ← entry point: read the specs in order, then progress.md
├── progress.md ← living session status + the run log
├── .gitignore ← ignores kdb/ and wiki/ CONTENTS (folders kept via .gitkeep)
├── README.md
│
├── ai_specs/ ← the specs — source of truth, tracked in git
│   ├── overview.md ← 1. goal and overall idea
│   ├── domain_knowledge.md ← 2. terminology, rules, constraints
│   ├── oracle.md ← 3. which Oracle to follow + the intended bias
│   ├── collection_techniques.md ← 4. where & how documents are downloaded
│   ├── distillation_techniques.md ← 5. how knowledge is distilled
│   ├── output_format.md ← 6. the shape of distilled output
│   └── batch_process.md ← 7. scheduled jobs + backup
│
├── kdb/ ← collected raw documents (contents gitignored, backed up)
├── wiki/ ← distilled output (contents gitignored, backed up)
└── src/ ← the pipeline — tracked in git
    ├── collect.py ← downloads sources into kdb/
    ├── distill.py ← distills kdb/ into wiki/ per the specs
    ├── build_index.py ← builds the retrieval index over wiki/
    ├── backup.py ← backs up kdb/ and wiki/
    ├── paths.py ← every folder location, in one place
    └── run_batch.py ← orchestrates the nightly pipeline

Each spec file names its own audience at the top, in the order Claude Code should read them.

CLAUDE.md
Root · Entry Point

Tells Claude Code to read the seven specs in order, then progress.md. Also carries the folder rules and the behavior rules — including the instruction never to neutralize the Oracle's bias.

progress.md
Root · Session Memory + Run Log

What is done, in progress, and blocked — plus the run log table, one row per pipeline run. Read first every session, since neither the pipeline nor the assistant remembers the last one.

ai_specs/overview.md
Audience: Business Sponsor

The goal, who asks the questions, who maintains the pipeline, what "done" looks like, non-goals, and success metrics.

ai_specs/domain_knowledge.md
Audience: AI Assistant + Team

Domain summary, key terminology as this Oracle uses it, domain rules, common misconceptions, entities worth extracting, and known gaps in the canon.

ai_specs/oracle.md
Audience: Project Definer + AI

The lens. Oracle type, philosophy, the canon, explicitly rejected sources, voice and register, the key questions it must answer, and the bias and stance rules.

ai_specs/collection_techniques.md
Audience: Engineer + collect.py

The source inventory, how each type is downloaded, what gets filtered out at collection time, dedup by content hash, freshness policy, and failure handling.

ai_specs/distillation_techniques.md
Audience: Engineer + distill.py

The method: which techniques are switched on, merge and dedup policy, quality guardrails, chunking strategy, model choices, and cost controls.

ai_specs/output_format.md
Audience: The Distiller · The Contract

The exact shape of every file written into wiki/ — front matter, section order, and the sources footer. The single most consequential file in the project.

ai_specs/batch_process.md
Audience: DevOps / Engineer

The four nightly stages and what each reads and writes, the schedule, incremental behavior, backup and retention, logging, and failure isolation.

Section 04

The Nightly Pipeline

SD-KDP does its real work while you sleep. src/run_batch.py runs four stages in order, and a scheduler — cron, Task Scheduler, or a scheduled task — triggers it once a night.

STAGE 01

Collect

Downloads the Oracle's canon into kdb/, hashing each document so unchanged sources are skipped.

STAGE 02

Distill

Reads kdb/ and four specs, then writes articles and FAQ into wiki/ in the Oracle's voice.

STAGE 03

Index

Chunks and embeds everything in wiki/ into a vector index the chatbot queries.

STAGE 04

Backup

Snapshots kdb/ and wiki/, which git does not track, and prunes old snapshots.

Script Reads Writes
src/collect.py collection_techniques.md, kdb/links/ kdb/
src/distill.py kdb/, oracle.md, domain_knowledge.md, distillation_techniques.md, output_format.md wiki/
src/build_index.py wiki/ .index/
src/backup.py kdb/, wiki/ backups/

Two rules the orchestrator enforces

A single bad source must never abort the run. A dead link or an unparseable PDF is logged and the run continues. Unattended jobs that fail completely because of one bad input are unattended jobs nobody trusts.

Backup runs even when an earlier stage fails. If distillation blows up, the data you already collected still gets snapshotted. Every run appends a row to the run log in progress.md, with detailed logs under .state/runs/.

Why kdb/ and wiki/ are not in git

Both change every day — they are data, not code. Committing them would bloat the repository and bury real changes under churn. So the folders are tracked, via .gitkeep, while their contents are ignored, and the pipeline takes responsibility for backing them up instead.

What stays in git is the specs and the code — which together are everything needed to rebuild kdb/ and wiki/ from scratch.

If it is not in git, back it up on purpose. Gitignoring data is the right call, but it silently removes the safety net most students assume they have. backup.py keeps 14 timestamped snapshots by default — decide deliberately whether that is enough for your project.
Section 05

The Output Format Is the Contract

output_format.md deserves its own section, because it is the file students underestimate most. It defines the exact shape of every artifact written into wiki/: the front matter, the section order, and the mandatory sources footer.

Change it, and the entire wiki/ is reshaped on the next run — with no code changes at all. Adding a required section, switching to FAQ-only output, or introducing a glossary is a documentation edit, not an engineering task. That is the clearest demonstration in either framework of what "the spec is the source of truth" actually buys you.

Leader → drill-down

Every article is layered in a strict order, and the ordering is what makes answers fast to retrieve and easy to cite.

LevelWhat it holdsWho it serves
Leader The TL;DR, in the Oracle's voice — one to three sentences A reader who needs one glance
Body The overview and the direct answer Most questions, most of the time
Depth Details, examples, and what the Oracle rejects A reader going deep, or an answer that needs citing

Four rules hold across every artifact: faithfulness first — every claim traces to a source span; provenance always — an accurate sources footer, every time; self-contained answers — each FAQ answer stands alone; and no padding — a short source produces a short artifact.

Never fabricate an example. The format has an Examples section, but it is to be omitted when the source provides none. An invented example is the fastest way to turn a distilled knowledge base into a plausible-sounding liability.
Section 06

The Six-Step Workflow

From an empty scaffold to a knowledge base you can query.

  1. Declare Your Oracle

    Before anything else, decide whose lens this project commits to and write ai_specs/oracle.md. Name the philosophy, the canon, the rejected sources, the voice, and the key questions the Oracle must be able to answer. Those key questions become your acceptance test.

    Key question: can you name at least three sources this Oracle would reject? If not, you have chosen a topic, not an Oracle.

  2. Fill In the Seven Specs — Claude.ai

    Upload the SD-KDP template files to Claude.ai and describe your Oracle and your sources. Start with overview.md and oracle.md; the remaining five follow from them. Generate one file at a time and review each before moving on.

    Example prompt to Claude.ai

    "These are my OpenOwls SD-KDP template files. I want to build a distilled knowledge base for [the Oracle], drawing on [the canon], for readers who are [audience]. Please fill in overview.md first, following the template structure exactly."

  3. Implement collect.py and distill.py

    The scaffold ships these as stubs with the TODOs marked and the governing spec named in each docstring. Implement collection for your actual sources first — PDFs, URL lists, feeds — then distillation. requirements.txt lists candidate libraries, all commented out: you choose the PDF parser, the fetcher, the model provider, and the vector store.

  4. First Manual Run — One Source

    Run python src/run_batch.py by hand against a single source and read the output closely. Does it follow output_format.md exactly? Does it sound like the Oracle, or has it drifted to generic consensus? Does every claim trace to the source?

    When output looks wrong, fix the spec — not the output. Editing a generated file fixes one file for one day. Editing the spec fixes every file, on every future run.

  5. Schedule It Nightly

    Once a manual run is clean, hand it to a scheduler. Collection and distillation are hash-based, so only new or changed sources are reprocessed; --force rebuilds everything. Check the run log in progress.md the next morning.

  6. Query the Distilled Base

    Point your chatbot at the index built over wiki/ and ask the key questions from oracle.md. That is the acceptance test from overview.md: the right answers, in the Oracle's voice, sourced from the distilled base — not a generic averaged take.

    Example Claude Code session opener

    "Read ai_specs/ in the order listed in CLAUDE.md, then progress.md. Last night's run is in the run log. The next task is [task from progress.md]. Let's begin."

Section 07

Golden Rules for Distillers

Fix the spec, then re-run

The spec files are the source of truth. If the distilled output is wrong, the spec that produced it was ambiguous. Correct the spec and re-run — hand-editing files in wiki/ produces work that the next nightly run silently overwrites.

Never neutralize the Oracle's bias

Distilled answers that drift into balanced, hedged consensus have failed the project's whole purpose. If output stops sounding like the Oracle, treat it as a defect and tighten oracle.md or turn on stance reinforcement in distillation_techniques.md.

Every claim traces to a source

No outside facts, no invented examples, and an accurate sources footer on every artifact. A distilled base whose provenance cannot be checked is worse than no distilled base, because it looks authoritative.

Never commit kdb/, wiki/, or secrets

The data folders are gitignored on purpose and protected by backup.py instead. API keys live in .env, never in a spec file and never in a committed script.

Update progress.md after every session

Neither the pipeline nor the assistant remembers the previous session. Move finished items to done, note what is blocked, and keep the run log current — it is the only record of what the unattended job actually did.

Respect the sources you collect

Honor robots.txt and site terms, rate-limit your fetching, and record where every document came from. Collection is the one stage that touches systems you do not own.

Section 08

Motivation and Rationale

SD-KDP exists because a growing share of interesting student projects are not applications at all. They are attempts to read more material than a person can read and turn it into something answerable. That is a distinct engineering problem, and it deserves its own spec structure.

Method lineage

SD-KDP adapts Spec-Driven Development — specs first, in version control, used to brief the AI — from building software to building distilled knowledge. The habits transfer directly: name your audience, decide before you build, keep the decisions reviewable, and let the specs brief the machine rather than re-explaining yourself every session.

Each spec still mirrors a real role

As in OpenOwls SDD, every file has a named human audience. overview.md is written by a business sponsor. collection_techniques.md is a data engineer's document. distillation_techniques.md belongs to an ML engineer choosing methods and defending them. batch_process.md is an operations engineer's plan for work that runs while nobody is watching. And oracle.md has no equivalent in ordinary software work at all — it is closest to an editorial charter, which is exactly the kind of document engineers are rarely asked to write and increasingly need to.

Why declared bias is a teaching device

Students building AI tools are usually told to reduce bias. SD-KDP asks them to do something harder and more honest: choose a lens deliberately, write it down, name what it excludes, and label the output as that lens's view. Doing this once makes it permanently obvious that every knowledge system has a perspective — and that the dangerous ones are the systems whose perspective was never written down.

Why the pipeline runs unattended

Interactive work hides operational problems. A job that runs at 2am forces real questions: what happens when a source disappears, what happens when a stage fails halfway, how do you know the next morning whether it worked, and where does the data live if it is not in git. Those questions are the substance of production engineering, and a nightly distillation job is an unusually good place to meet them for the first time.
